# 레포 문서·운영 규칙

## 문서 구성과 원문 연결

폴더와 파일의 배치는 [README](../README.md#위치)를 따릅니다. 기능 문서는 `features/<FEAT-ID>/`의 고정 경로에서 전체 적용 내용을 유지하고, 업데이트별 계획은 `updates/<UPD-ID>/`에 둡니다. 기능·화면·문서 ID와 위치 색인은 `registry/`에서 관리합니다.

같은 논리 문서의 Notion 후속 페이지나 Figma 새 버전 페이지는 같은 ID·파일 경로에 연결합니다. 현재·이전 원문 URL과 내용 해시·마지막 변경 업데이트·관련 파일 위치는 `manifest.json`에 기록합니다. 실제 변경과 출처·버전 변경만 diff에 남기고, 원문 복제를 새 기능으로 간주하지 않습니다.

기획 문서는 확인된 원문 내용을 반영합니다. 가상의 기능·ID·정책·결정 이유를 만들어 채우지 않습니다. 실제 문서가 없는 경로는 README의 예정 구조로만 안내하며 색인은 빈 상태를 허용합니다.

## 화면·버전·ID

Figma의 기준 구조는 업데이트별 파일 → 버전별 페이지 → 기능 Section → 화면 Frame입니다. 여러 기능이 한 페이지를 공유할 수 있고, 공통 컴포넌트는 별도 영역과 의존 관계로 구분합니다.

와이어프레임은 `vM.m`, 화면 설명은 `vM.m.p`입니다. 설명의 앞 두 자리는 해당 기능이 선택한 와이어프레임 버전과 일치해야 합니다. 신규·레거시 최초 등록과 와이어프레임 변경 후 설명은 `vM.m.0`으로 두고, 설명만 바뀌면 마지막 자리를 올립니다. 다른 기능만 바뀐 Figma 페이지를 본 기능의 새 버전으로 자동 간주하지 않으며 번호가 건너뛸 수 있습니다.

버전은 문서·메타데이터에 기록하고 파일명에 붙여 복제하지 않습니다. 기존 원문 버전 표기는 출처로 보존하며, 관리용 와이어프레임 버전과 Figma 내부 버전 ID는 구분합니다.

기능·화면·문서 ID를 Notion·Figma 원문에 강제로 넣지 않습니다. 화면요소 참조 ID는 와이어프레임과 설명 양쪽에 명시하고 같은 의미에서는 유지합니다. 복제 페이지의 Figma native node ID는 새 위치를 가리켜야 합니다. 레거시에 원래 없던 요소 ID는 미확정으로 표시하며, 원문에 있는 것처럼 기록하지 않습니다. 세부 요구사항·정책 조항의 영구 매핑은 만들지 않습니다.

## 계승·정책·폐기

| 변경 유형 | 반영 기준 |
| --- | --- |
| 유지 | 기존 내용·원문·선택 버전을 계승하고 업데이트 목록에 표시 |
| 일부 수정 | 같은 ID·경로에서 명시한 변경만 반영 |
| 전면 개편 | 같은 역할의 기능은 ID·경로 유지. 역할이 다른 새 기능은 새 ID와 대체 관계 연결 |
| 폐기 | 명시적으로 승인한 변경에서 현행 본문을 폐기 안내·과거 참조로 대체하고 색인·정책 연결도 정리 |

이번 업데이트에서 언급하지 않은 기능을 폐기로 해석하지 않습니다. 공통 정책을 기본으로 적용하고 기능별 예외는 명시·승인된 것만 적용합니다. 공통 정책이 바뀌면 계승 기능에 미치는 영향도 검토합니다.

결정 이유는 확인 가능한 기록이 있을 때 `decisions/`에 연결합니다. 근거 미기록이나 AI 제안 미채택만으로 문서 등록·PR·병합을 차단하지 않습니다. 제안·미결사항·확정 기획을 구분하고 문서 간 충돌은 양쪽 근거와 적용 범위를 제시합니다.

## PR에 포함할 정보

PR은 [기획용 양식](../.github/pull_request_template.md)에 따라 변경 목적·대상 문서·적용 원문·검토 결과·미결사항을 설명합니다. 기존 기획 최초 등록과 신규 기능 기획을 구분하고 관련 문서·정책·버전·계승에 미치는 영향을 표시합니다.

운영 설정 PR은 바뀌는 레포 관리 규칙과 실제 확인 결과를 설명하며, 해당하지 않는 기능 ID·원문·화면 버전 항목은 생략합니다. 빈 항목·가상의 이슈·확인하지 않은 검증 결과를 채워 넣지 않습니다.

커밋의 유형·한글 작성·한 커밋 한 작업 기준은 [커밋 작성 기준](commit-convention.md)을 따릅니다. 원문을 수정하더라도 같은 변경의 열린 PR에서 검토를 이어가고, 이미 병합된 변경의 후속 작업은 새 PR로 구분합니다.

## 업데이트 최종본

업데이트 종료 시 `updates/<UPD-ID>/release.json`에 선택 문서·버전·계승 출처를 기록합니다. 담당자가 최종화 PR을 병합한 커밋에 완료 태그를 두고, 완료 업데이트의 문서 링크는 해당 태그·승인 커밋으로 고정합니다. 완료 태그는 이동시키지 않습니다.

다음 업데이트는 새 PRD·IA·변경 목록을 만들고 기존 기능·정책 경로를 유지합니다. 태그는 레포에 저장된 내용을 보존하며 외부 Notion·Figma 원문을 자동 백업한 것으로 보지 않습니다.

## 작업 브랜치

`main`은 최신 승인 기획을 담습니다. 작업 브랜치는 최신 `main`에서 만들고 변경은 PR로 반영합니다. 업데이트별 상시 브랜치를 두지 않으며, 업데이트 구분은 `updates/` 폴더와 완료 태그로 관리합니다.

| 작업 | 브랜치 형식 | 예시 |
| --- | --- | --- |
| 기능·업데이트·정책 등 기획 산출물 작업 | `planning/<대상>-<작업명>` | `planning/FEAT-001-screen-description`, `planning/UPD-001-prd` |
| ID가 없는 기존 기획의 최초 등록 | `planning/<작업명>` | `planning/legacy-search-register` |
| 운영 안내·도구·설정 작업 | `chore/<작업명>` | `chore/pr-template` |

예시 ID는 형식 설명용입니다. 실제 등록된 ID가 있으면 사용하고 브랜치 이름을 위해 새 ID를 만들지 않습니다. 작업명은 짧은 영문 소문자·숫자·하이픈으로 작성하며, 같은 이름이 이미 사용됐으면 작업명이나 숫자 접미사로 구분합니다. `planning`은 브랜치의 용도로, 커밋의 `add`·`change`·`fix`와 별개입니다. 기존 열린 PR의 브랜치는 이번 규칙에 맞추려고 이름을 바꾸지 않습니다.

독립적으로 검토·승인할 수 있는 기능이나 변경 건을 PR 단위로 삼습니다. 같은 변경에 필요한 공통 정책·화면 설명·색인은 함께 포함할 수 있습니다. 다른 기능이 미완성이어도 해당 기능은 별도로 승인할 수 있으며, 원문 수정 후에는 같은 열린 PR을 갱신합니다.

## 병합과 브랜치 정리

1. PR의 대상은 `main`으로 두고 담당자가 변경 내용·미결사항을 확인한 뒤 직접 병합합니다. 별도 승인자나 AI 지적의 전부 해결을 필수 조건으로 두지 않습니다.
2. 기본 병합 방식은 **Create a merge commit**입니다. 작업별 커밋을 보존하고 병합 커밋 제목은 PR의 한글 제목으로 작성합니다. 독립적인 작업 여러 개를 Squash로 한 커밋에 합치지 않습니다. 자동 병합은 설정하지 않습니다.
3. 병합 후 담당자가 PR의 병합 상태와 작업 브랜치의 마지막 커밋까지 반영됐는지 확인하고, GitHub의 **Delete branch**로 완료된 작업 브랜치를 삭제합니다. 새 미반영 커밋이 생겼다면 해당 작업을 먼저 확인합니다. `main`과 업데이트 완료 태그는 보존합니다.
4. 브랜치 삭제 후에도 병합된 커밋과 PR 이력으로 변경을 조회합니다. 다음 변경은 최신 `main`에서 새 작업 브랜치·PR로 시작합니다. 과거 업데이트의 최종 문서 링크는 삭제할 작업 브랜치가 아닌 완료 태그·승인 커밋을 가리키게 합니다.

위 병합 방식과 정리 절차는 운영 지침입니다. GitHub의 다른 병합 버튼을 비활성화하거나 브랜치 자동 삭제를 설정한 상태를 뜻하지 않습니다.
