# 기획 문서 커밋 작성 기준

## 기본 형식

```text
유형: 한글 변경 요약
```

기획 산출물에는 `add`·`change`·`fix`, 문서 관리 작업에는 `chore`를 사용합니다. 유형은 네 가지로 제한하고 `docs`·`clarify`·`remove`·`migrate`·`revert`를 별도 유형으로 두지 않습니다. 제목·본문은 한글로 작성하며 파일명·ID·도구 이름은 기존 표기를 유지합니다.

유형은 작업 목적을 설명합니다. 승인 여부·개발 완료·배포 상태·문서 버전·알림 대상을 뜻하지 않습니다. 기획 문서는 이 레포의 산출물이므로 Markdown 파일이라는 이유로 관리 작업으로 분류하지 않습니다.

## 한 커밋에는 한 가지 작업

**한 커밋에는 독립적으로 검토하거나 되돌릴 수 있는 한 가지 작업만 담습니다.** 같은 날 수정했거나 같은 기능에 속한다는 이유만으로 서로 다른 작업을 묶지 않습니다.

- 파일 수로 나누지 않습니다. 하나의 정책 변경에 필요한 명세·화면 설명·관련 정책·원문 링크·버전·색인은 함께 반영합니다. 같은 변경을 파일별로 쪼개 문서 간 모순을 만들지 않습니다.
- 토스트 추가와 별개의 글자 수 제한 변경은 커밋을 나눕니다. 기획 변경과 README·자동화 설정 변경도 나눕니다.
- 신규 기능을 설명하는 데 필요한 명세와 첫 화면설계는 하나의 `add` 작업으로 묶을 수 있습니다. 기능 전체를 제목에 붙여 독립적인 후속 변경까지 한꺼번에 담지는 않습니다.
- 기존 내용을 정정하는 작업과 새 정책을 결정하는 작업은 별개라면 나눕니다. 변경 결과를 유지하기 위해 반드시 함께 고쳐야 하는 내용은 같은 커밋에 담습니다.
- 하나의 PR에 여러 커밋이 들어갈 수 있습니다. 여러 작업을 요청받으면 먼저 목적별로 나누고, 관련된 커밋만 같은 PR에서 검토합니다. 서로 다른 커밋 유형을 합친 복합 접두어는 쓰지 않습니다.
- 되돌릴 때는 대상 커밋과 범위를 확인합니다. 후속 작업이 의존하면 필요한 정합성 수정도 같은 복원 작업에 포함하며, 기존 완료 태그를 이동하거나 이력을 자동 재작성하지 않습니다.

## 유형별 판단 기준

| 유형 | 뜻 | 사용 기준 |
| --- | --- | --- |
| `add` | 기획 문서·항목 추가 | 기존 기획을 관리 구조에 맞춰 최초 등록하거나 새 기능·요구사항·정책·시나리오·화면·와이어프레임을 추가 |
| `change` | 기존 기획 산출물 변경 | 등록된 문서의 구조 개편, 기존 기준·화면의 수정·삭제·폐기, 설명·근거 보완 |
| `fix` | 기획 오류 정정 | 확인된 기존 기준과 다른 표기·누락·모순·화면요소 연결을 바로잡음 |
| `chore` | 레포 운영·관리 | 루트 README·AGENTS·CLAUDE·운영 가이드·PR 양식·스킬·자동화·설정의 추가·수정·오류 정정 |

### 헷갈릴 때의 순서

1. 운영 안내·관리 도구·설정을 바꾸면 `chore`입니다. 문서의 역할로 판단하며 파일명이나 확장자만으로 분류하지 않습니다. 예를 들어 기능 README에 실제 요구사항을 추가·수정하면 `add`·`change`·`fix` 중 작업에 맞는 유형을 사용합니다.
2. 기획 산출물의 오류를 확인된 기준에 맞게 바로잡으면 `fix`입니다. 오류 정정의 기준이 불명확하면 임의로 정책을 선택하지 말고 미결사항으로 보고합니다.
3. 기존 기획을 GitHub 관리 구조에 맞춰 처음 등록하거나 새 기획 항목을 추가하면 `add`입니다. 이미 등록된 기획 문서의 구조·내용을 바꾸면 `change`입니다. 예를 들어 기존 글자 수 제한을 바꾸면 `change`, 정해지지 않았던 제한 정책을 새로 정하면 `add`입니다.

기존 기획의 최초 등록은 새 기능 출시를 뜻하지 않습니다. 제목에는 기존 기능의 최초 등록임을 적고, PR에는 재구성한 범위와 서비스 동작 변경 여부를 밝힙니다. 등록과 별개로 새 정책을 결정하거나 기존 오류를 정정하면 작업별 커밋으로 분리합니다. 원문을 새 Notion 페이지·Figma 페이지로 복제했다는 이유만으로 같은 논리 문서를 다시 최초 등록하지 않습니다.

개발자의 요청이나 AI 지적을 받았다는 사실만으로 `fix`가 되지는 않습니다. 기존에 정해진 인증 시나리오가 문서에서 빠졌다면 `fix`, 새 시나리오를 결정했다면 `add`입니다. 설명 보강에 새로운 조건이 들어가면 단순 표현 보완이 아니라 실제 추가·변경 내용을 제목에 적습니다.

기존 화면의 와이어프레임을 수정하면 `change`, 새 화면을 처음 그리면 `add`입니다. 기존 승인본의 추출·등록 오류를 바로잡는 경우는 `fix`입니다. 원문 링크·버전·색인만 정리하는 독립적인 관리 작업은 `chore`이며, 실제 기획 변경에 필요한 갱신은 해당 커밋에 포함합니다.

## 작성 예시

아래는 형식 예시이며 실제 서비스 정책을 정의하는 내용이 아닙니다.

| 상황 | 커밋 제목 예시 |
| --- | --- |
| 기능 추가 | `add: 알림 설정 기능 기획 추가` |
| 기존 기능의 스펙 일부 변경 | `change: 인증번호 재전송 대기 시간 변경` |
| 새 토스트 메시지 추가 | `add: 저장 완료 토스트 추가` |
| 새로 결정한 인증 시나리오 추가 | `add: 토큰 만료 후 재인증 시나리오 추가` |
| 기존에 정해졌으나 문서에서 누락된 시나리오 복원 | `fix: 명세에서 누락된 재인증 시나리오 반영` |
| 새 로딩 화면 추가 | `add: 검색 결과 로딩 화면 추가` |
| 동작은 유지하고 설명 보강 | `change: 검색 결과 정렬 기준 설명 보강` |
| 정해지지 않았던 글자 수 제한 정책 추가 | `add: 소개글 최대 글자 수 정책 추가` |
| 새 화면 와이어프레임 작성 | `add: 알림 설정 화면 와이어프레임 작성` |
| 기존 와이어프레임 수정 | `change: 알림 설정 화면의 저장 버튼 위치 변경` |
| 확인된 기준에 맞게 화면 설명의 모순 해소 | `fix: 화면 설명의 인증번호 유효시간 모순 정정` |
| 기능 폐기 | `change: 기존 간편 로그인 방식 폐기` |
| README·운영 가이드 수정 | `chore: 기획 문서 조회 안내 보완` |
| 기존 기획을 재구성하여 최초 등록 | `add: 기존 검색 기능의 명세와 화면 설명 최초 등록` |
| 이미 등록된 기획 문서의 구조 개편 | `change: 검색 기능 문서의 정책과 화면 설명 분리` |
| 관리 자동화 오류 수정 | `chore: 원문 수집 시 후속 페이지 연결 누락 수정` |

## 괄호는 선택 사항

[Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/)의 `유형(적용 범위): 설명`에서 괄호는 유형의 하위 분류가 아니라 적용 대상(scope)입니다. 이 레포는 유형을 기획 업무에 맞게 정하며, 기본적으로 괄호를 생략합니다.

필요하면 등록된 기능 ID 등을 넣을 수 있습니다: `change(FEAT-001): 인증번호 재전송 대기 시간 변경`. 제목을 위해 새 ID나 대상 분류 목록을 만들지 않습니다.

## PR·알림과의 관계

PR 제목은 전체 검토 목적을 요약합니다. 같은 목적의 추가·수정이 함께 있으면 `change`, 기존 기획의 최초 등록이나 새 기능을 완성하기 위한 문서 작업이면 `add`처럼 전체 목적에 맞는 유형 하나를 씁니다. 독립적인 운영 작업은 별도 커밋·PR로 분리합니다. PR 본문에는 신규·유지·일부 수정·전면 개편·폐기를 구체적으로 표시합니다.

되돌림도 별도 유형 없이 기획을 이전 상태로 바꾸면 `change`, 오류를 바로잡으면 `fix`, 관리 작업의 복원이면 `chore`를 사용하고 대상 커밋을 본문에 남깁니다. 최종 병합은 담당자가 합니다.

Discord 알림은 담당자의 기획 PR `main` 병합과 실제 변경 범위로 판단합니다. 운영 안내·설정·도구·색인만 바뀐 PR은 제외합니다. 팀 공지에는 제목의 구체적인 변경 내용을 활용하며 접두어만으로 동작 변경 여부를 단정하지 않습니다. 설명만 보강했다면 기대 동작은 유지된다고 적습니다.

변경 전후·이유·영향·실제 근거 링크는 필요할 때 커밋 본문과 PR에 적습니다. 근거는 선택 사항이며 없는 이유를 만들어내지 않습니다. 기존 커밋은 이번 기준에 맞추려고 자동 재작성하지 않습니다. 이 기준은 작성 지침으로 적용하며 새 CI·커밋 강제 검사는 추가하지 않습니다.
